How a checkout
becomes an order.

A guided walk through the critical path of the checkout service — the functions that matter, the edges that carry risk, and the one place where the flow loops back on itself.

MKMira K.·updated 2h ago·snapshot a3f10c2

The checkout path begins at a single HTTP handler and ends at a payment capture. In between, five modules exchange calls. Most of the code is straightforward; the interesting part is where inventory reservation and payment authorization share a failure boundary.

The entry point

CheckoutController.checkout has one caller and five callees. It is deliberately thin: validate, price, create, and handle errors. The graph is small enough to follow at a glance, but the fan-out is where the first risk appears.

The first branch is validation. It is boring on purpose: reject malformed carts before spending money. The second branch prices the cart, which reads coupons and tax rules. The third creates an order, which reserves inventory and authorizes payment.

The graph is not the documentation. It is the index into the documentation.

createOrder is the hinge

OrderService.createOrder is the highest-risk function in the path. It has three callers, four callees, and a failure path that must release inventory if authorization fails. In the current implementation, that release is guarded by a try/catch. The graph makes the guard visible; the code makes it correct.

A cycle in pricing

Pricing contains a small cycle: priceCart → applyCoupon → taxFor → priceCart. It is not necessarily a bug, but it makes the order of operations hard to reason about. A future refactor should move coupon validation out of the tax path.

Where to go next

Start at the entry point, follow the highlighted path, then open the blast radius for createOrder. The review queue has the cycle and the two untested call sites.
